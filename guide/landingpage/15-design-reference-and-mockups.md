# 15. Design Reference and Mockup Guidance

## 15.1 Required visual deliverables

Create a cohesive set of visual references for:
1. Desktop home page, 1440px wide.
2. Desktop feature presentation section.
3. Interactive demo workspace.
4. Pricing page in paid mode.
5. Home page in free mode (pricing absent, layout balanced).
6. Contact page.
7. Mobile home page.
8. Mobile demo presentation.

These are design references, not screenshots of a running application. Replace them with verified screenshots after implementation.

## 15.2 Home page composition

- Top navigation with compact brand mark.
- Large left-aligned hero copy.
- Two clear CTA buttons.
- Right-side product mockup with a three-pane research-writing workspace.
- Small supporting capability strip.
- Feature cards in a balanced grid.
- Product showcase sections with screenshots.
- Workflow steps.
- Template cards.
- Conditional pricing block.
- FAQ and final CTA.

## 15.3 Demo composition

Browser-like application frame:
- Project tree on left.
- LaTeX source editor in middle.
- Rendered academic PDF on right.
- Build status and log strip below.
- Toolbar with sample engine selector and preview action.
- Clearly visible “Interactive preview — sample project” label.

## 15.4 Paid pricing state

- Three illustrative plan cards only if the product owner approves plan names/prices and the plans exist in backend.
- During design mockup stage, use clearly marked placeholders such as “Example plan” and “Price configured by administrator”; do not publish invented commercial prices.
- Feature comparison should be concise.
- No false scarcity or urgency.

## 15.5 Free pricing state

- No pricing heading, empty container or pricing navigation.
- The home page should flow directly from templates/FAQ to final CTA or another meaningful section.
- Do not leave a blank gap where pricing would have been.

## 15.6 Contact page

- Clear title and explanation.
- Form on one side, configured contact details or response expectations on the other.
- Do not invent a postal address, phone number or support email.
- Form states: idle, submitting, validation error, success, server error.

## 15.7 Production screenshot policy

Only label an image “screenshot” when captured from the running application. Generated visuals must be called “mockup”, “concept” or “design reference”. Do not use mockups as evidence that a feature already exists.
